# Ops Implementation Plan (spec phase 13, sequenced first)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the architecture built in phases 1–9 actually run in the shipped deployment — the FastAPI app, the TaskIQ worker, and the scheduler — and put pgbouncer into the pooling mode the engine already assumes.

**Architecture:** One image, three commands. `docker-compose.yml` gains `api` (uvicorn, scalable), `worker` (taskiq worker, scalable) and `scheduler` (taskiq scheduler, exactly one), all built from the existing `Dockerfile` and separated only by `command:`. pgbouncer moves from session to transaction pooling, which the SQLAlchemy engine was already configured for. Every service gets a healthcheck and honest dependency ordering.

**Tech Stack:** Docker Compose, uvicorn 0.52.4, TaskIQ 0.12.5, pgbouncer (`edoburu/pgbouncer`), Prometheus, Grafana, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-23-scalable-architecture-design.md` — sections 4 (process topology), 16 (observability), 19 (deployment), 21 phase 13.

---

## Why this plan exists, stated plainly

`Dockerfile` ends in `CMD ["python", "-m", "bot"]`. `bot/__main__.py` runs long polling and its own docstring says *"Never a production path."* So in the shipped stack:

- The FastAPI app never starts. No `/webhook`, no `/health/live`, no `/health/ready`, no `/metrics`, no `/webapp`, no `/api/webapp/*`. The Mini App built in phases 9–10 cannot run at all.
- The compose `bot` service publishes `${WEBHOOK_PORT}` and Prometheus scrapes `bot:8080/metrics`, both pointing at a process that never binds the port.
- `docker-compose.yml` contains **no worker and no scheduler service**. Every TaskIQ task is dead: `payments:reconcile`, `payments:expire_premium`, `analytics:flush`, `broadcast:start`, `broadcast:chunk`, `export:users`. Analytics events are `LPUSH`ed to Redis and `LTRIM`med at 100 000, so they are silently discarded rather than shipped. Premium never expires. The admin broadcast command enqueues work nothing consumes.
- `bot/core/di.py`'s engine sets `statement_cache_size=0` and `prepared_statement_cache_size=0` with the comment *"pgbouncer runs in transaction pooling mode"* — while compose sets `POOL_MODE=session`. The code and the deployment disagree.

Two of the ten tasks completed in the payments/Mini App plan — the premium expiry sweep and Stars reconciliation — have **zero production effect** until this plan lands.

## Scoping decision, now obsolete — the Flask stack is already gone

This plan originally kept the Flask `admin` service alive, because spec phase 10 (SQLAdmin)
had not run. **It has now run**, ahead of the remaining ops tasks, at the human's request to
finalise the structure. So:

- `admin/` no longer exists; there is no `admin` compose service and no `${ADMIN_PORT}`.
- `flask*`, `psycopg2-binary`, `gunicorn` and `tablib` are removed from `pyproject.toml`.
- The panel is served by the `api` service at `${WEBHOOK_PORT}/admin`, mounted by
  `setup_admin` in `bot/entrypoints/api.py`.

Any step below that talks about the `admin` service, `admin/Dockerfile`, or the Flask panel
is describing a state that no longer exists. Those steps are corrected in place; if you find
one that is not, **it is stale — report it rather than recreating the service.**

## Already done, do not redo

Spec section 19 says phase 13 "removes the `CConnection` prepared-statement-name hack entirely". **It is already gone** — `grep -rn CConnection bot/` returns nothing, and `bot/database/database.py` no longer exists. Phases 1–6 removed it and set the two statement-cache options. This plan only has to flip pgbouncer's side.

## Global Constraints

- Python floor **3.14** (`requires-python = ">=3.14,<4.0"`); Docker image `ghcr.io/astral-sh/uv:0.12-python3.14-alpine`.
- All tooling through `uv` — `uv sync`, `uv run`; never bare `pip`. Run `uv sync` after any `pyproject.toml` change.
- Logging is `from loguru import logger`; stdlib `logging` is forbidden in new/edited code.
- ruff runs `select = ["ALL"]`, line-length 120, `fix = true`, `unsafe-fixes = false`. **`uv run ruff check .` mutates files** — run it before reading your diff, not after.
- mypy is strict and must reach 0 errors.
- **No tests.** Do not write tests, do not add a test runner, do not create `tests/`. Verification is throwaway scripts and live `docker compose` runs, deleted afterwards.
- Commits are conventional-commit; **never** add a `Co-Authored-By` trailer.
- Compose topology: `api` scalable, `worker` scalable, `scheduler` **exactly one instance**.
- Telegram will not load a Mini App over plain HTTP; `localhost` does not work on mobile clients.

## Task 1: Run the API in Docker instead of long polling

**Files:**
- Modify: `Dockerfile:19`
- Modify: `docker-compose.yml` (the `bot` service; `admin.depends_on`; `migrator.depends_on`; every service's `ports:` mapping)
- Modify: `configs/prometheus/prometheus.yml` (the `tgbot` job target)
- Modify: `Makefile` (the `logs` and `compose-exec` help text)
- Modify: `.env.example`, `README.md`

**Interfaces:**
- Produces: a compose service named **`api`** listening on container port **8080**, serving `/health/live`, `/health/ready`, `/metrics`, `/webhook`, `/webapp`, `/api/webapp/*`. Tasks 2, 4, 5 and 6 all refer to it by that name.

- [ ] **Step 1: Change the image's default command**

`Dockerfile:19` is currently:

```dockerfile
CMD ["python", "-m", "bot"]
```

Replace with:

```dockerfile
# The API entrypoint, not `python -m bot` (long polling) — polling is a development
# path and serves neither /metrics, /health/* nor the Mini App. The container port is
# fixed at 8080; compose maps ${WEBHOOK_PORT} to it, so the host port stays configurable
# while Prometheus can scrape a stable `api:8080`.
CMD ["uvicorn", "bot.entrypoints.api:app", "--host", "0.0.0.0", "--port", "8080"]
```

**Do not add `--workers N`.** Each worker process runs the lifespan independently, which would call `set_webhook` once per worker and register N schedulers' worth of startup work. The spec scales the API by container replicas, not in-process workers.

**Do not add `--proxy-headers`.** `bot/api/webhook.py` already reads `X-Forwarded-For` itself, gated on the `trust_proxy_headers` setting, and takes the last entry deliberately. Letting uvicorn rewrite `request.client.host` as well would make that gate meaningless — a header the operator has not opted into trusting would reach the allowlist check anyway.

- [ ] **Step 2: Rename the `bot` compose service to `api`**

In `docker-compose.yml`, the service is currently:

```yaml
  bot:
    build:
      context: .
      dockerfile: ./Dockerfile
    image: bot:latest
    container_name: ${COMPOSE_PROJECT_NAME}-bot
    restart: always
    env_file:
      - .env
    ports:
      - ${WEBHOOK_PORT}:${WEBHOOK_PORT}
    networks:
      - app
      - monitoring
    depends_on:
      - pgbouncer
      - redis
```

Replace with:

```yaml
  api:
    build:
      context: .
      dockerfile: ./Dockerfile
    image: bot:latest
    container_name: ${COMPOSE_PROJECT_NAME}-api
    restart: always
    env_file:
      - .env
    # Host port is configurable; the container port is always 8080 so Prometheus and
    # the healthchecks below can address it without reading .env.
    ports:
      - ${WEBHOOK_PORT}:8080
    networks:
      - app
      - monitoring
    depends_on:
      - pgbouncer
      - redis
```

Keep `image: bot:latest`. Tasks 2 builds `worker` and `scheduler` from the same image, and the `migrator` service already reuses it.

- [ ] **Step 2b: Stop every service from conflating its host port with its container port**

Every published port in `docker-compose.yml` is written `${X_PORT}:${X_PORT}`:

```
      - ${WEBHOOK_PORT}:${WEBHOOK_PORT}
      - ${ADMIN_PORT}:${ADMIN_PORT}
      - ${DB_PORT}:${DB_PORT}
      - ${REDIS_PORT}:${REDIS_PORT}
      - ${PROMETHEUS_PORT}:${PROMETHEUS_PORT}
      - ${GRAFANA_PORT}:${GRAFANA_PORT}
```

The right-hand side is the **container** port, which is fixed by each image, and the
variable is simultaneously the app's connection port (`DB_PORT=5432` is what
`DB_HOST=pgbouncer` is dialled on). So changing `DB_PORT` to dodge a host collision
does not move the host binding — it points the mapping and the application at a port
nothing inside the container listens on, and the stack fails in a way that reads as a
database outage.

That is not hypothetical on a developer machine: **ports 5432, 6379 and 5000 are
already occupied on the machine this plan was written on** (5000 is macOS's AirPlay
Receiver by default), so `docker compose up` cannot bind them as written.

Pin every container port to the image's real one and leave only the host side
configurable:

```yaml
      - ${WEBHOOK_PORT}:8080        # api        (already done in Step 2)
      - ${DB_PORT}:5432             # pgbouncer  (listens on 5432 regardless of DB_PORT)
      - ${REDIS_PORT}:6379          # redis
      - ${PROMETHEUS_PORT}:9090     # prometheus
      - ${GRAFANA_PORT}:3000        # grafana
```

**`DB_PORT` and `REDIS_PORT` must stay 5432 and 6379** in `.env` — inside the compose
network the app dials `pgbouncer:5432` and `redis:6379`, and those are container
ports, not host ports. Add a comment in `.env.example` saying exactly that, next to
both variables, because the obvious reading of "DB_PORT" is the opposite.

To verify locally against occupied host ports, change only the **host** side:

```bash
# in .env — host bindings only; the app still dials pgbouncer:5432 and redis:6379
DB_PORT=5432        # leave as-is: this is the container port the app dials
REDIS_PORT=6379     # leave as-is
```

If a host port is taken, edit the left-hand side in `docker-compose.yml` for that one
verification run and revert before committing, or stop the conflicting container if it
is yours. **Do not stop containers you did not start** — on this machine there are
`postgres` and `redis` containers belonging to something else.

## Task 2: Add the worker and scheduler services

**Files:**
- Modify: `docker-compose.yml`
- Modify: `Makefile`
- Modify: `README.md`, `.env.example`

**Interfaces:**
- Consumes: the `api` service and `image: bot:latest` from Task 1.
- Produces: compose services **`worker`** and **`scheduler`**. Task 4 adds healthchecks to both.

**This is the task that resurrects five dead subsystems.** Until it lands, `payments:expire_premium`, `payments:reconcile`, `analytics:flush`, `broadcast:*` and `export:users` are registered on a broker nothing consumes.

- [ ] **Step 1: Add both services**

Place them immediately after `api` in `docker-compose.yml`:

```yaml
  worker:
    image: bot:latest
    build:
      context: .
      dockerfile: ./Dockerfile
    restart: always
    command: taskiq worker bot.entrypoints.worker:broker
    env_file:
      - .env
    networks:
      - app
    depends_on:
      - pgbouncer
      - redis
    # Safe to scale: `docker compose up -d --scale worker=3`. The broker is a Redis
    # list, so consumers compete for jobs rather than duplicating them. No
    # container_name — a fixed name makes the service unscalable.

  scheduler:
    image: bot:latest
    build:
      context: .
      dockerfile: ./Dockerfile
    restart: always
    command: taskiq scheduler bot.entrypoints.scheduler:scheduler
    env_file:
      - .env
    networks:
      - app
    depends_on:
      - redis
    # EXACTLY ONE INSTANCE. Never scale this service. `bot/entrypoints/scheduler.py`
    # says so in its own docstring: every replica reads the same cron labels and
    # enqueues its own copy of each job at each tick. `payments:expire_premium` is
    # idempotent and `payments:reconcile` is read-only, so today the damage is
    # duplicate work and duplicate alerts — but `broadcast:start` is neither, and a
    # second scheduler would fan out a broadcast twice.
    deploy:
      replicas: 1
```

Both services deliberately omit `container_name` (except where a fixed name already exists elsewhere in the file) and publish no ports.

- [ ] **Step 2: Add Makefile conveniences**

```bash
asyncio.run(m())

```

Expected registered task names include `payments:reconcile`, `payments:expire_premium`, `analytics:flush`, `broadcast:start`, `broadcast:chunk`, `export:users`. Expected schedules include `analytics:flush cron=* * * * *`, `payments:reconcile cron=*/15 * * * *`, `payments:expire_premium cron=7 * * * *`.

**A registered task whose schedule label is never read would pass the first check and still never run** — that is why both checks are here, not just the first.

## Task 3: Switch pgbouncer to transaction pooling

**Files:**
- Modify: `docker-compose.yml` (the `pgbouncer` service)
- Modify: `README.md`

**Interfaces:**
- Consumes: the `api` and `worker` services from Tasks 1–2.
- Produces: nothing other tasks import; this is a configuration change verified behaviourally.

**The code already assumes this.** `bot/core/di.py`'s engine passes `connect_args={"statement_cache_size": 0, "prepared_statement_cache_size": 0}` with the comment *"pgbouncer runs in transaction pooling mode"*, while compose sets `POOL_MODE=session`. One of the two is wrong, and the spec says the deployment is.

Session mode holds one Postgres backend per client connection for the connection's whole life. With `api` and `worker` each holding a pool and both scaling by replica, Postgres connection count multiplies by replica count — which is exactly what pgbouncer is supposed to prevent.

- [ ] **Step 1: Flip the pooling mode**

The `pgbouncer` service's environment is currently:

```yaml
      - POOL_MODE=session
      - MAX_DB_CONNECTIONS=0
      - DEFAULT_POOL_SIZE=40
```

Replace those three lines with:

```yaml
      # Transaction pooling: a server connection is held only for the duration of a
      # transaction, so N app replicas no longer mean N Postgres backends. The
      # SQLAlchemy engine is already configured for this (statement_cache_size=0 and
      # prepared_statement_cache_size=0 in bot/core/di.py) — server-side prepared
      # statements cannot be reused across transactions in this mode.
      - POOL_MODE=transaction
      # A real ceiling, not 0 (unlimited). This is the number the whole point of
      # pgbouncer rests on: it must stay below Postgres's own max_connections (100 by
      # default) with headroom for the migrator and any psql sessions.
      - MAX_DB_CONNECTIONS=50
      - DEFAULT_POOL_SIZE=20
```

- [ ] **Step 2: Check for session-scoped state that transaction mode would break**

Transaction pooling silently breaks anything that assumes a session outlives a transaction: `LISTEN`/`NOTIFY`, session-level advisory locks, `SET` outside a transaction, and `WITH HOLD` cursors. Search before trusting:

```bash
grep -rniE "listen |notify |advisory_lock|pg_advisory|WITH HOLD|SET SESSION" bot/ migrations/ | grep -v __pycache__
```

Expected: no hits. If you find one, **stop and report it** — that is a genuine blocker for this task, not something to work around.

- [ ] **Step 3: Verify the async path through pgbouncer under concurrency**

A single query proves almost nothing here; the failure mode is a *reused* server connection carrying a prepared statement from a previous transaction. Drive concurrent sessions:

```bash
make compose-up
sleep 20
docker compose exec api python -c "
import asyncio
from dishka import Scope
from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession
from bot.core.config import get_settings
from bot.core.lifespan import lifespan

async def one(ctx, i):
    async with ctx.container(scope=Scope.REQUEST) as rc:
        s = await rc.get(AsyncSession)
        r = await s.execute(text('select :n::int'), {'n': i})
        return r.scalar_one()

async def main():
    async with lifespan(get_settings()) as ctx:
        for round_ in range(5):
            got = await asyncio.gather(*(one(ctx, i) for i in range(20)))
            assert got == list(range(20)), got
        print('  100 pooled queries across 5 rounds: OK')
asyncio.run(main())
"
```

Expected: `100 pooled queries across 5 rounds: OK`. A `DuplicatePreparedStatementError` or `InvalidSQLStatementNameError` here means a statement cache is still enabled somewhere — report it rather than papering over it.

- [ ] **Step 4: Verify the admin panel still works through transaction mode**

The Flask panel and its psycopg2 driver are gone; the panel is now SQLAdmin inside the `api`
service, on the **same async engine** as the bot. That removes the second-driver risk this
step originally existed for, but it does not remove the need to check — SQLAdmin issues its
own queries (list pagination, counts, the dashboard aggregate) that no other code path does.

```bash
curl -fsS -o /dev/null -w "  /admin        -> %{http_code}\n" -L localhost:8080/admin
curl -fsS -o /dev/null -w "  /admin/user/list -> %{http_code}\n" localhost:8080/admin/user/list
docker compose logs api --tail 30
```

Unauthenticated requests redirect to the login page rather than 200 — that is correct, and a
302/307 here is a pass. What must NOT appear in the log is `DuplicatePreparedStatementError`
or `InvalidSQLStatementNameError`; either means a statement cache is still enabled somewhere.

- [ ] **Step 5: Confirm the connection ceiling is actually enforced**

```bash

  "select count(*) as backends from pg_stat_activity where datname = '$DB_NAME';"

  "select count(*) as backends from pg_stat_activity where datname = '$DB_NAME';"
```

Expected: the second count is not three times the first. That contrast is the point of the whole task — record both numbers in your report.

Tear down with `make compose-down`.

- [ ] **Step 6: Document it and commit**

In `README.md`, note that pgbouncer runs in transaction mode and that the engine's two disabled statement caches exist because of it — so nobody "cleans up" either half in isolation.


## Task 4: Healthchecks and honest dependency ordering

**Files:**
- Modify: `docker-compose.yml` (every service)

**Interfaces:**
- Consumes: `api`, `worker`, `scheduler` from Tasks 1–2.
- Produces: a stack where `docker compose up` waits for real readiness. Task 5's CI workflow depends on this.

`grep -n healthcheck docker-compose.yml` currently returns **nothing** — no service has one. `depends_on` without a condition waits only for the container to be *created*, not for the service inside it to accept connections, so `api` races Postgres on every cold start.

- [ ] **Step 1: Add healthchecks to the infrastructure services**

```yaml
  postgres:
    # ... existing keys ...
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${DB_USER} -d $${DB_NAME}"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 10s

  redis:
    # ... existing keys ...
    healthcheck:
      test: ["CMD-SHELL", "redis-cli ping | grep -q PONG"]
      interval: 5s
      timeout: 3s
      retries: 10

  pgbouncer:
    # ... existing keys ...
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -p 5432 -U $${DB_USER}"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 10s
```

The `$$` is required: a single `$` would be interpolated by Compose itself before the container ever sees it.

- [ ] **Step 2: Add healthchecks to the application services**

The image is Alpine-based and has no `curl`; it does have `wget`.

```yaml
  api:
    # ... existing keys ...
    healthcheck:
      # /health/live only — the process is up. Readiness (/health/ready) checks
      # Postgres and Redis, so using it here would take the API container unhealthy
      # during a database blip and make Docker restart a process that is fine.
      test: ["CMD-SHELL", "wget -qO- http://127.0.0.1:8080/health/live >/dev/null || exit 1"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 20s

  worker:
    # ... existing keys ...
    healthcheck:
      # There is no HTTP surface here. Assert the two things a worker actually needs:
      # that the app imports, and that the Redis the broker uses answers. Deliberately
      # NOT `broker.<something>.ping()` — `ListQueueBroker` exposes no public client
      # attribute (checked: nothing matching client/redis/pool on the class), so
      # reaching into its internals would make this healthcheck a hostage to a
      # taskiq-redis refactor.
      test:
        - CMD-SHELL
        - >-
          python -c "import asyncio;from redis.asyncio import Redis;from bot.core.config import get_settings;
          asyncio.run(Redis.from_url(get_settings().redis.url).ping())" || exit 1
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 20s
```

Give `scheduler` the same healthcheck as `worker`.

Run that one-liner inside the container before trusting it. A healthcheck that always passes is worse than none, because it makes an unhealthy service look supervised:

```bash
docker compose exec worker python -c "import asyncio;from redis.asyncio import Redis;from bot.core.config import get_settings;asyncio.run(Redis.from_url(get_settings().redis.url).ping());print('  redis ping OK')"
```

- [ ] **Step 3: Fix the dependency graph**

Replace the bare `depends_on` lists with conditions, and put the migrator where it belongs:

```yaml
  migrator:
    # ... existing keys ...
    depends_on:
      pgbouncer:
        condition: service_healthy

  api:
    depends_on:
      pgbouncer:
        condition: service_healthy
      redis:
        condition: service_healthy
      migrator:
        condition: service_completed_successfully

  worker:
    depends_on:
      pgbouncer:
        condition: service_healthy
      redis:
        condition: service_healthy
      migrator:
        condition: service_completed_successfully

  scheduler:
    depends_on:
      redis:
        condition: service_healthy

  admin:
    depends_on:
      pgbouncer:
        condition: service_healthy
```

Two corrections are embedded here and both matter:

1. `migrator` previously declared `depends_on: [bot]`, i.e. it waited for the application before migrating. Now the application waits for migrations to **complete successfully**, which is the actual requirement.
2. `admin` previously depended on `bot`. It has no reason to wait for the API — it needs the database. Pointing it at `pgbouncer` removes a false dependency that would otherwise make an API failure look like an admin failure.

`migrator` has `restart: "on-failure"`, which is compatible with `service_completed_successfully` — it retries until it exits 0.

- [ ] **Step 4: Verify readiness gating actually works**

```bash

```

Expected: `docker compose ps` shows `(healthy)` for postgres, redis, pgbouncer, api, worker, scheduler; `migrator` shows `Exited (0)`.

Then prove the gate is real rather than incidental — start from nothing and watch the ordering:

```bash

docker compose up -d

docker compose logs api --tail 5
```

Expected: `api` does not report a database connection error at startup, because it did not start until pgbouncer was healthy and the migrator had exited 0. On the pre-change stack this was a race.

- [ ] **Step 5: Give in-flight work time to drain on shutdown**

Spec section 19 requires that "graceful shutdown drains in-flight updates before exit". Docker sends `SIGTERM` and then `SIGKILL`s after **10 seconds** by default, which is shorter than a slow Telegram call plus a database commit. Add to `api`, `worker` and `scheduler`:

```yaml
    # Docker's default is 10s. uvicorn stops accepting connections on SIGTERM and waits
    # for in-flight requests; the worker finishes the task it is executing. A SIGKILL
    # midway through `PaymentService.record` would abort the transaction — recoverable,
    # since the payment insert only flushes and the credit commits them together — but a
    # SIGKILL between `refund_star_payment` and the local write is not.
    stop_grace_period: 30s
```

Verify the drain is real rather than assumed:

```bash
make compose-up && sleep 20
docker compose stop api worker
docker compose logs api --tail 15
docker compose logs worker --tail 15
```

Expected: the `api` log shows uvicorn's graceful shutdown and the application lifespan running its shutdown half (`emit_shutdown`), not an abrupt end. Expected exit code 0, not 137 (which is SIGKILL — the grace period expired):

```bash
docker inspect -f '{{.State.ExitCode}}' $(docker compose ps -aq api)
```

## Task 5: CI smoke test for the compose stack

**Files:**
- Create: `.github/workflows/compose-smoke.yml`

**Interfaces:**
- Consumes: everything Tasks 1–4 produce.
- Produces: a CI job that fails when the shipped stack does not come up.

The repo's CI lints and builds an image. Nothing ever runs the stack — which is exactly how a
`Dockerfile` that started the wrong process survived nine phases of work.

### The constraint that shapes this task

**The `api` container cannot start without a real bot token.** `bot/core/lifespan.py` calls
`await bot.get_me()` and lets `TelegramUnauthorizedError` escape, and `set_default_commands()`
calls `set_my_commands`. With a well-formed but fake token the container exits 3 before serving
anything. This was found while verifying Task 1 and reproduced:

```
aiogram.exceptions.TelegramUnauthorizedError: Telegram server says - Unauthorized
Application startup failed. Exiting.
```

**Do not "fix" this by making `get_me()` non-fatal.** That is worse than the problem: a
genuinely invalid token would then start silently in production, and failing loudly at startup
is the behaviour that catches a mistyped secret before users do. The strictness is correct; CI
has to work around it, not remove it.

The worker and scheduler are unaffected — neither calls the Telegram API at startup. Their
`WORKER_STARTUP` hook builds the dishka container, and `Bot` is only constructed lazily when a
task asks for it. So the split is:

| Provable with no credentials | Needs a real throwaway bot token |
|---|---|
| image builds; postgres, redis, pgbouncer healthy; migrator exits 0; worker and scheduler healthy; tasks registered AND scheduled | `api` healthy; `/health/ready`, `/metrics`, `/webapp`, `/admin` |

- [ ] **Step 1: Write the credential-free job**

```yaml
name: Compose smoke test

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  smoke:
    name: Boot the stack (no Telegram credentials required)
    runs-on: ubuntu-latest
    timeout-minutes: 15

    steps:
      - uses: actions/checkout@v7

      - name: Create a .env for CI
        run: |
          cp .env.example .env
          # Well-formed so pydantic-settings validates. The api service is deliberately
          # NOT started in this job — see the job below — because lifespan calls get_me()
          # and this token is not real.
          sed -i 's|^BOT_TOKEN=.*|BOT_TOKEN=110201544:AAHdqTcvCH1vGWJxfSeofSAs0K5PALDsaw|' .env
          sed -i 's|^USE_WEBHOOK=.*|USE_WEBHOOK=False|' .env
          sed -i 's|^ADMIN_SECRET_KEY=.*|ADMIN_SECRET_KEY=ci-only-not-a-real-key-0123456789|' .env

      - name: Build the image
        run: docker compose build

      - name: Start infrastructure, migrator, worker and scheduler
        run: |
          docker compose up -d --wait --wait-timeout 300 postgres pgbouncer redis worker scheduler

      - name: Show what came up
        if: always()
        run: docker compose ps -a

      - name: Migrations ran to completion
        run: |
          test "$(docker compose ps -a --format '{{.Service}} {{.ExitCode}}' | awk '$1=="migrator"{print $2}')" = "0"
          docker compose logs migrator | tail -5

      - name: Scheduled tasks are registered AND scheduled
        run: |
          docker compose exec -T worker python -c "
          import bot.tasks
          from bot.tasks import broker
          names = set(broker.get_all_tasks())
          need = {'payments:reconcile', 'payments:expire_premium', 'analytics:flush'}
          missing = need - names
          assert not missing, f'not registered: {missing}'
          print('registered OK:', sorted(need))
          "
          docker compose exec -T scheduler python -c "
          import asyncio, bot.tasks
          from taskiq.schedule_sources import LabelScheduleSource
          from bot.tasks import broker
          async def m():
              s = LabelScheduleSource(broker); await s.startup()
              got = {x.task_name for x in await s.get_schedules()}
              need = {'payments:reconcile', 'payments:expire_premium', 'analytics:flush'}
              missing = need - got
              assert not missing, f'registered but never scheduled: {missing}'
              print('scheduled OK:', sorted(need))
          asyncio.run(m())
          "

      - name: Dump logs on failure
        if: failure()
        run: docker compose logs --tail 200

      - name: Tear down
        if: always()
        run: docker compose down -v
```

Both task checks are needed and neither replaces the other: a task can be registered on the
broker while its cron label is never read, in which case it is listed and still never runs.

- [ ] **Step 2: Add the credentialed job, skipped when the secret is absent**

A second job in the same file, gated on a repository secret so it runs on `push` to `main` and
on same-repo pull requests, and skips on forks — where secrets are unavailable by design:

```yaml

      - name: Skip without a token

          else

          fi

```

When it does run, bring up the whole stack with `--wait` and assert:
