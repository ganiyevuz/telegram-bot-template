# Telegram Notifier Implementation Plan (spec phase 11)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Operational alerting into a Telegram admin chat — from the bot's own failure paths and from an authenticated HTTP endpoint other systems can post to — without letting an alert storm starve user traffic.

**Architecture:** `NotifierService.send(level, title, body, fingerprint)` writes an alert to a TaskIQ task rather than to Telegram, so nothing on a request path ever blocks on delivery. Every alert carries a fingerprint and is suppressed by a Redis `SET NX EX` cooldown that counts what it swallowed. Delivery goes through the same outbound token bucket as user messages, so alerts can never outrank them.

**Tech Stack:** aiogram 3.30, TaskIQ, Redis, FastAPI, dishka, `hmac`/`hashlib` from the standard library.

**Spec:** `docs/superpowers/specs/2026-08-23-scalable-architecture-design.md` — section 17.

---

## Why suppression is the hard part

A crash loop is the normal case for this feature, not the exception. Without suppression, one
failing handler emits an alert per update: thousands of messages, the outbound rate limiter
saturated, and — because `OutboundRateLimiter._wait` *sleeps* until the shared global bucket
refills rather than shedding — every ordinary user reply queued behind them. The alerting
feature would become the outage.

So the fingerprint is not a nicety. Every alert carries one — exception type, module and line
for errors; source and key for inbound alerts — and the notifier does
`SET notify:{fingerprint} NX EX <cooldown>`. During a cooldown it increments a counter instead
of sending. When the window expires the next alert reports `(x147 suppressed)` rather than
replaying the backlog.

## Global Constraints

- Python floor **3.14**; all tooling through `uv` — never bare `pip`. `uv sync` after any
  `pyproject.toml` change, and commit `uv.lock` with it.
- Logging is `from loguru import logger`; stdlib `logging` is forbidden.
- ruff `select = ["ALL"]`, line-length 120, `fix = true`, `unsafe-fixes = false`.
  **`uv run ruff check .` mutates files** — run it before reading your diff.
- mypy strict, 0 errors.
- **No tests.** Do not write tests, do not create `tests/`. Verify with throwaway scripts and
  live runs against private containers, deleted afterwards.
- Conventional commits; **never** a `Co-Authored-By` trailer.
- **Runtime annotation hazard** — this codebase's most-repeated defect (10 occurrences). dishka,
  aiogram, FastAPI and SQLAlchemy resolve annotations at RUNTIME via `get_type_hints()`. Any type
  in a handler signature, a FastAPI dependency, a dishka provider or a SQLAlchemy `Mapped[...]`
  must be a real module-level import, never under `if TYPE_CHECKING:`. Where ruff's TC rules push
  a runtime-needed import into `TYPE_CHECKING`, add a targeted `# noqa: TC00x`, as
  `bot/core/di.py` and `bot/handlers/payments.py` already do.
- **No new dependencies.** The HMAC is `hmac` + `hashlib` from the standard library.
- **The `api` container cannot start with a fake `BOT_TOKEN`** — `bot/core/lifespan.py` calls
  `get_me()` and lets `TelegramUnauthorizedError` escape. Drive the FastAPI app in-process with
  `TestClient` and a stubbed `AiohttpSession.make_request` instead of running that container.

## Task 1: Levels, settings, and the cache keys

**Files:**
- Create: `bot/notifier/__init__.py`, `bot/notifier/levels.py`
- Modify: `bot/core/config.py`, `bot/cache/keys.py`, `.env.example`

**Interfaces:**
- Produces: `AlertLevel` (a `StrEnum` with `INFO`, `WARNING`, `ERROR`, `CRITICAL`), `AlertLevel.format(title, body, suppressed)` returning the message text; `NotifierSettings` reached as `settings.notifier`; `CacheKeys.notify(fingerprint)` and `CacheKeys.notify_count(fingerprint)`.

- [ ] **Step 1: Add `NotifierSettings`**

Follow the nested-settings style already used by `WebAppSettings` and `PaymentSettings` in
`bot/core/config.py` — a `BaseSettings` subclass with `env_prefix`, attached to `Settings`.

```python
class NotifierSettings(BaseSettings):
    model_config = SettingsConfigDict(**_ENV, env_prefix="NOTIFIER_")

    chat_id: int | None = None
    topic_id: int | None = None          # forum thread, optional
    secret: SecretStr = SecretStr("")    # HMAC key for POST /api/notify
    cooldown_seconds: int = 300
```

`chat_id` defaults to `None` and that is the off switch: with no chat configured the notifier
must become a no-op rather than an error. An operator who has not set it up should not get a
stream of failures *about* alerting.

Add all four to `.env.example` with a comment on each. Say plainly that `NOTIFIER_SECRET` being
empty **disables** `POST /api/notify` rather than leaving it unauthenticated — see Task 4.

- [ ] **Step 2: Add the cache keys**

`bot/cache/keys.py` has a `CacheKeys` class of `@classmethod`s over a `_key(*parts)` helper.
Add two, matching that style exactly:

```python
    @classmethod
    def notify(cls, fingerprint: str) -> str:
        """Cooldown marker. Present = an alert with this fingerprint was sent recently."""
        return cls._key("notify", fingerprint)

    @classmethod
    def notify_count(cls, fingerprint: str) -> str:
        """How many alerts this fingerprint swallowed during the current cooldown."""
        return cls._key("notify", fingerprint, "count")
```

- [ ] **Step 3: Create `bot/notifier/levels.py`**

```python
from __future__ import annotations

import enum
import html


class AlertLevel(enum.StrEnum):
    INFO = "info"
    WARNING = "warning"
    ERROR = "error"
    CRITICAL = "critical"

    @property
    def emoji(self) -> str:
        return {
            AlertLevel.INFO: "ℹ️",
            AlertLevel.WARNING: "⚠️",
            AlertLevel.ERROR: "🔥",
            AlertLevel.CRITICAL: "🚨",
        }[self]

    def format(self, title: str, body: str, suppressed: int = 0) -> str:
        """The message text. Everything caller-supplied is HTML-escaped.

        The bot's default parse mode is HTML (bot/telegram/factory.py), and both `title`
        and `body` can carry an exception message, a URL, or whatever a caller POSTed to
        /api/notify. An unescaped `<` makes Telegram reject the entire message — so the
        alert about a failure would itself fail, silently, exactly when it is needed.
        """
        tail = f"\n\n<i>(x{suppressed} suppressed)</i>" if suppressed else ""
        return f"{self.emoji} <b>{html.escape(title)}</b>\n<pre>{html.escape(body)}</pre>{tail}"
```

The escaping is the point of this step. This repo has already shipped one bug of exactly this
shape — an unclosed `<b>` in a locale broke `/export_users` — and an alert path that dies on its
own payload is worse, because nothing else will report it.

- [ ] **Step 4: Verify the formatting and the escape**

Write a throwaway script, run it, paste output, delete it. It must show:
- each level renders its own emoji;
- `suppressed=0` produces no tail, `suppressed=147` produces `(x147 suppressed)`;
- a title containing `<script>` and a body containing `a < b && c > d` come out escaped, with no
  raw `<` surviving outside the tags the formatter itself emits.

For the last one, assert on the absence of the *input's* angle brackets, not on the absence of
all `<` — the template legitimately contains `<b>` and `<pre>`.

```bash

git add bot/notifier/ bot/core/config.py bot/cache/keys.py .env.example
git commit -m "feat(notifier): alert levels, settings and cooldown cache keys"
```

## Task 2: The delivery task

**Files:**
- Create: `bot/tasks/notify.py`
- Modify: `bot/tasks/__init__.py`

**Interfaces:**
- Consumes: `AlertLevel` (Task 1).
- Produces: `deliver_alert(level: str, title: str, body: str, suppressed: int) -> bool`, registered as `notify:deliver`.

**This is the only code in the feature that talks to Telegram.** Everything else enqueues.

- [ ] **Step 1: Write the task**

Follow `bot/tasks/analytics.py` exactly for shape: `get_container()`, then
`await container.get(X)` for APP-scoped dependencies. `Bot` and `Settings` are both APP-scoped,
so this task needs no REQUEST scope at all.

```python
@broker.task(task_name="notify:deliver")
async def deliver_alert(level: str, title: str, body: str, suppressed: int = 0) -> bool:
    """Send one alert. Returns False when the notifier is not configured."""
```

Behaviour:
- Resolve `Settings`; if `settings.notifier.chat_id` is `None`, log at DEBUG and return `False`.
  Not a warning — an unconfigured notifier is a choice, not a fault, and warning on every alert
  would be its own noise.
- Resolve `Bot` and `send_message(chat_id, text, message_thread_id=settings.notifier.topic_id)`.
  `Bot.send_message` does accept `message_thread_id` — **confirmed** against the installed
  aiogram. Pass it only when `topic_id` is set: sending `None` is harmless, but sending a real
  thread id to a non-forum chat is rejected by Telegram.
- Catch `TelegramAPIError`, log a warning, return `False`. **An alert that fails to send must
  never raise**: this runs in a worker, and a raising task is retried or dead-letters, turning
  one failed alert into a loop.

- [ ] **Step 2: Register the module**

Add `notify` to the trailing import at the bottom of `bot/tasks/__init__.py` (the line carrying
`# noqa: E402, F401`). Without it TaskIQ never discovers the task and every alert enqueues into
nothing.

- [ ] **Step 3: Verify it delivers and that it fails safe**

Private containers (`nt2-pg`, `nt2-rd`). Stub `AiohttpSession.make_request` to capture outbound
methods. Show:
- with `NOTIFIER_CHAT_ID` set, `deliver_alert("error", "t", "b", 0)` produces exactly one
  `SendMessage` to that chat with the formatted text;
- with `NOTIFIER_TOPIC_ID` also set, the outbound method carries `message_thread_id`;
- with `NOTIFIER_CHAT_ID` unset, it returns `False` and produces **zero** outbound calls;
- when the stub raises `TelegramForbiddenError`, the task returns `False` and **does not raise**.

That last case is the one that matters: assert on the return value, not just that no traceback
appeared — a task that swallows the error but re-raises something else looks the same in a log.

- [ ] **Step 4: Lint and commit**

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy
git add bot/tasks/
git commit -m "feat(notifier): TaskIQ delivery task for alerts"
```

## Task 3: The service, with cooldown suppression

**Files:**
- Create: `bot/notifier/service.py`
- Modify: `bot/core/di.py`

**Interfaces:**
- Consumes: `AlertLevel`, `CacheKeys.notify*` (Task 1); `notify:deliver` (Task 2).
- Produces: `NotifierService.send(level, title, body, fingerprint) -> bool` (True when an alert was enqueued, False when suppressed or unconfigured); an APP-scoped dishka provider.

- [ ] **Step 1: Write the service**

```python
class NotifierService:
    """Fingerprinted alerting with a Redis cooldown.

    `send` never blocks on Telegram and never raises: it decides whether this alert is
    the first of its kind in the cooldown window, and if so enqueues `notify:deliver`.
    Callers are error handlers and health checks — the last places that should acquire a
    new way to fail.
    """

    def __init__(self, redis: Redis, settings: NotifierSettings) -> None: ...

    async def send(self, level: AlertLevel, title: str, body: str, fingerprint: str) -> bool: ...
```

The cooldown, in order:
1. If `settings.chat_id` is `None`, return `False` immediately. No Redis call, no enqueue.
2. `SET notify:{fingerprint} 1 NX EX cooldown_seconds`.
3. **If it set** (first in the window): read and delete `notify:{fingerprint}:count` — that is the
   number swallowed since the last send — and enqueue `notify:deliver` with `suppressed` set to
   it. Return `True`.
4. **If it did not set** (inside the window): `INCR notify:{fingerprint}:count`, give that key a
   TTL comfortably longer than the cooldown so it cannot outlive its marker forever, and return
   `False`.

Read-and-delete the counter, not read-then-reset-later: two replicas can pass step 3 for
different fingerprints concurrently, and a non-atomic reset would drop counts. Use `GETDEL` —
**confirmed available**: this project pins redis-py 8.1.0 and `Redis.getdel` exists.

**Catch `RedisError` and fail OPEN — enqueue the alert.** The alternative is that a Redis outage
silences alerting at exactly the moment something is wrong. Duplicate alerts during an outage
are an acceptable price; silence is not. `bot/middlewares/dedup.py` and `throttling.py` both
document the same trade-off in the other direction, and the difference is deliberate: dropping a
throttle check degrades to unthrottled, while dropping an alert degrades to blind.

- [ ] **Step 2: Provide it through dishka**

Add an APP-scoped provider in `bot/core/di.py` beside the existing ones. It needs `Redis` and
`Settings`, both already APP-scoped. Import `NotifierService` at module level — `di.py` carries
`# ruff: noqa: TC001, TC002` precisely because dishka resolves these annotations at runtime.

- [ ] **Step 3: Verify the suppression arithmetic**

Private Redis (`nt3-rd`). Stub the task's `.kiq` so nothing needs a broker. Show, with a short
cooldown (2s) so the test is quick:

```
1st send                 -> enqueued=True,  suppressed=0
2nd..10th send           -> enqueued=False  (9 suppressed)
after the cooldown, 11th -> enqueued=True,  suppressed=9
12th send                -> enqueued=False
different fingerprint    -> enqueued=True   (independent cooldown)
chat_id unset            -> enqueued=False, and ZERO redis calls
redis raising            -> enqueued=True   (fails open)
```

The `suppressed=9` line is the whole feature: it proves the counter survived the window and was
consumed exactly once. An implementation that reports `0` there is silently dropping the count,
and every other line above would still pass.

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy
git add bot/notifier/ bot/core/di.py
git commit -m "feat(notifier): fingerprinted alerts with Redis cooldown suppression"
```

## Task 4: `POST /api/notify`

**Files:**
- Create: `bot/api/notify.py`
- Modify: `bot/entrypoints/api.py`, `bot/middlewares/metrics.py`

**Interfaces:**
- Consumes: `NotifierService` (Task 3).
- Produces: route `POST /api/notify` returning **202**; counter `NOTIFY_REJECTIONS` labelled `reason`.

**This is a public write surface.** It is authenticated by an HMAC over the raw request body
with a shared secret, plus a timestamp header to bound replay. It only ever enqueues; it never
executes anything a caller supplies.

- [ ] **Step 1: Write the route**

Request body: `{"level": "error", "title": "...", "body": "...", "source": "...", "key": "..."}`
as a pydantic model. The fingerprint is `f"{source}:{key}"` — the spec's rule for inbound alerts.

Headers: `X-Signature` (hex HMAC-SHA256 of the **raw body bytes**, keyed by `NOTIFIER_SECRET`)
and `X-Timestamp` (unix seconds).

Order of checks, and it matters:
1. If `settings.notifier.secret` is empty → **404**, not 401. An unconfigured endpoint should not
   advertise that it exists. Record `reason="disabled"`.
2. Timestamp missing, unparseable, or more than 300 seconds from now (either direction) → 401,
   `reason="stale"`. Both directions: a clock-skewed caller far in the future is as suspect as a
   replayed request from the past.
3. Signature missing or not matching → 401, `reason="signature"`.
4. Body not matching the model → 422 (FastAPI's default).

Compute the HMAC over `f"{timestamp}.".encode() + raw_body` so the timestamp is *inside* the
signature. Signing only the body lets an attacker replay a captured request forever by changing
the header. Read the raw body with `await request.body()` — **not** the parsed model, whose
re-serialisation will not match byte-for-byte.

Use `hmac.compare_digest`. This project has fixed that exact timing bug twice already, on the
webhook secret and the Mini App `initData`.

Every rejection returns the same body. Increment `NOTIFY_REJECTIONS.labels(reason=...)` with a
**closed** set of reasons — never the supplied `source`, which is attacker-controlled and would
give the counter unbounded cardinality.

- [ ] **Step 2: Add the counter and mount the router**

Add `NOTIFY_REJECTIONS` to `bot/middlewares/metrics.py` beside the existing `tgbot_*` families,
matching their naming. Mount the router in `create_app()` beside `health`, `metrics`, `webhook`
and the webapp routes.

Use `FromDishka[NotifierService]` with the `DishkaRoute` route class, as `bot/webapp/routes.py`
does — dishka's FastAPI integration is already wired.

- [ ] **Step 3: Verify authentication as a contrast**

Drive the app with `TestClient` (needs `httpx2`; `uv run --with httpx2`). Show:

```
no secret configured        -> 404
valid signature + timestamp -> 202, and the service was called once
tampered body, same sig     -> 401
wrong secret                -> 401
missing X-Signature         -> 401
timestamp 10 min old        -> 401
timestamp 10 min in future  -> 401
replay of a valid request within the window -> 202   (by design: idempotency is the
                                                       notifier's cooldown, not the endpoint's)
```

The `202` line is the guard — without it, "everything returns 401" also satisfies every other
row. And assert the service was actually *called*, not merely that the status was 202: a route
that returns 202 and does nothing passes a status-only check.

```bash
git add bot/api/ bot/entrypoints/api.py bot/middlewares/metrics.py
git commit -m "feat(notifier): HMAC-authenticated POST /api/notify"
```

## Task 5: Wire the internal sources

**Files:**
- Modify: `bot/handlers/errors.py`, `bot/api/health.py`, `bot/core/lifespan.py`, `bot/tasks/broadcast.py`

**Interfaces:**
- Consumes: `NotifierService` (Task 3).
- Produces: alerts from the four sources the spec names.

The spec's internal sources: the `dp.errors` handler reports critical exceptions; readiness
transitions from `/health/ready`; broadcast completion; process startup and shutdown.

- [ ] **Step 1: The error handler**

`bot/handlers/errors.py`'s `on_error` already catches everything, increments `HANDLER_ERRORS` and
returns `True`. Add an alert with fingerprint
`f"{type(exc).__name__}:{module}:{lineno}"` taken from the traceback's last frame — that is the
spec's rule, and it means one alert per distinct crash site rather than per update.

**`on_error` takes only `event: ErrorEvent` today — it injects nothing.** I checked; there is no
existing pattern in this file to copy. So the first thing to establish is *how* it can reach the
service, and the answer is not obvious: `setup_dishka(..., auto_inject=True)` wires `FromDishka`
onto router observers via a `router.startup` hook, and `router.error()` is an observer — but
whether the error observer is covered is a question to answer by running it, not by reasoning.

Try `FromDishka[NotifierService]` in the signature first and **verify an alert actually fires
from a real raised exception**. If it does not, aiogram passes middleware `data` to error
handlers as keyword arguments, so accepting the container or the service by name from `data` is
the fallback. Say in your report which mechanism you used and how you confirmed it.

Note the trap this project has hit repeatedly: `feed_update()` alone does not fire
`router.startup`, so an injected parameter silently goes unfilled and the handler raises
`TypeError: ... missing 1 required positional argument`. Call `await dp.emit_startup(bot=bot)`
first in any throwaway harness.

**If the alert itself fails, the handler must still return `True`** — wrap it. An error handler
that raises turns every handled error into an unhandled one, and `on_error` returning `True` is
what makes the webhook answer 200 instead of making Telegram retry.

- [ ] **Step 2: Readiness transitions**

`/health/ready` already checks Postgres and Redis. Alert on the **transition**, not on each
probe: a load balancer polls this every few seconds and an alert per probe is a flood. Keep the
last known state in a module-level variable and alert only when it changes — ready→not-ready at
`ERROR`, not-ready→ready at `INFO`. Fingerprint `health:ready`.

Module-level state is per-process and that is correct here: each replica reports its own
transitions, and the cooldown collapses the duplicates.

- [ ] **Step 3: Startup, shutdown, and broadcast completion**

- `bot/core/lifespan.py`: `INFO` on startup with the bot username, `INFO` on shutdown.
  Fingerprints `lifecycle:startup` / `lifecycle:shutdown`.
- `bot/tasks/broadcast.py`: `INFO` when a broadcast finishes, with the counts it already logs.
  Fingerprint `broadcast:complete`.

Startup and shutdown alerts fire on **every replica**, so with three replicas a rolling deploy
produces six. That is the cooldown's job; do not add a second suppression mechanism.

- [ ] **Step 4: Verify each source fires once**

For each of the four, trigger the condition and assert exactly one `notify:deliver` enqueue with
the expected fingerprint. Then the contrast that matters for readiness: probe `/health/ready`
five times while healthy and assert **zero** alerts, then break Redis and probe again and assert
exactly **one**. Probing five times and getting five alerts is the bug this step exists to catch.

- [ ] **Step 5: Lint and commit**
